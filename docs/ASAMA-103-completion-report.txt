JWT AND REFRESH-TOKEN IMPLEMENTATION
--------------------------------------
Access tokens
  - Short-lived JWTs, signed HS256
  - Bound to session_id (sid claim) — revocation is immediate; every request re-checks the session row
  - Required claims validated: exp, iat, sub, sid, jti, type, iss, aud
  - Issuer: asama.ai   Audience: asama.ai/api

Refresh tokens
  - 384-bit opaque random strings (secrets.token_urlsafe(48))
  - Stored only as SHA-256 hex digests in refresh_sessions.token_hash
  - Rotated on every use; old session row marked revoked_reason=rotated
  - Family-based reuse detection: replaying any rotated token revokes all sessions in the family

Password hashing
  - stdlib hashlib.scrypt (N=16384, r=8, p=1, dklen=64, salt=16 bytes random)
  - Self-describing versioned format: scrypt$N$r$p$<b64 salt>$<b64 digest>
  - Automatic rehash on login when cost parameters are outdated (needs_rehash)
  - Timing equalisation: dummy hash always evaluated when email is unknown
  - Cost parameter bounds enforced on parse to prevent memory exhaustion from tampered rows


ORGANIZATION AND ROLE AUTHORIZATION
--------------------------------------
Roles (descending privilege): owner > admin > member

Enforcement:
  - require_roles() dependency factory used in all protected routes
  - Active organization resolved server-side from refresh_sessions.active_organization_id
  - Membership re-validated against organization_members on every request — role changes apply immediately
  - Cross-tenant access returns 404 (not 403) — no information leakage about other tenants

Role boundary rules:
  - Owner membership cannot be deleted
  - Admins cannot grant admin role or remove other admins
  - Only owners can remove admins
  - Members can read but cannot manage membership or rename the organization
